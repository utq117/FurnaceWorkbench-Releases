# 工程设计与取舍

[返回项目首页](../README.md)

合炉工作台的核心问题是：如何让市场采集、组合求解和持续采购在普通 Windows 用户设备上协同工作，并提供可维护的授权、反馈和升级体验。

本文介绍工程思路，不公开内部接口、交易协议、凭据格式或保护机制的实现细节。

## 1. 本地计算与云端授权

配方搜索和持续监控会随着材料范围、挂单数量及运行时间增加负载。将它们放在客户端运行，可以让计算资源随用户设备分布；云端聚焦账号、订阅、设备与反馈等较轻的服务。

客户端在授权生命周期中管理后台任务，账号资料分别存储。核心模块进行原生编译，发行过程检查包内容，减少直接修改和误带个人资料的风险。原生编译提高逆向成本，不能保证不可破解。

这项选择也意味着需要认真处理用户设备差异、进程退出、网络变化及状态恢复，而不是只维护一套服务器运行环境。

## 2. 材料准备与约束求解

从“用户选择材料”到“可以运行求解”，中间需要统一平台物品标识、补全物品信息、整理挂单，并明确价格与磨损约束。

材料准备采用可取消的后台任务，并展示阶段进度。进度刷新使用轻量查询，避免每次刷新重复分析完整挂单池；前端避免重叠轮询。平台请求频率与求解过程分别管理。

配方求解提供精确和快速模式，对输出按原始精度复核数量及磨损要求。界面与结果区分可行解和当前快照内已证明的最优解，不把有限采集范围内的结果描述为整个市场的全局最优。

## 3. 采购与还价的状态管理

外部交易请求可能超时，超时并不能直接证明下单失败。系统需要区分未提交、已提交、结果未知和已完成等状态，再决定是否核对或继续操作。

还价记录持久化，同一挂单进行去重，并管理待处理请求占用的采购次数。重启后恢复已有记录的核对，不自动启动新的采购任务；超时取消仍遵守平台允许的条件。

市场配方购买单独选择收货 Steam 账号，预览与提交保持一致，并在确认环节再次显示。单次购买的选择不改写全局收货配置。

## 4. 少打扰用户的 AI 反馈

AI 的职责是把零散描述整理成可行动的信息：用户想改进什么、已经做过什么、缺少哪一步复现条件。

- 信息充分时直接确认，不强迫用户填写固定模板。
- 仅追问影响定位的关键缺口，通常一个问题。
- 自动回复标注“AI 初步回复”，不自动关闭反馈，也不承诺修复。
- 管理员已接手时，避免延迟完成的 AI 任务再次插话。

云端采用持久化任务、租约、重试上限、调用预算和结构校验。模型调用只使用反馈正文与精选帮助信息，并做基础敏感信息过滤；不自动附带用户配置或诊断日志。

## 5. 可重复的桌面交付

分发版从开发工程中生成经过裁剪的发行输入，按版本构建安装包。并行开发时固定构建输入，使测试与发布对应同一份内容。

发布前检查个人数据排除规则、运行依赖、程序启动与安装升级行为。GitHub 附件通过摘要核对后发布，QQ 上传后核对群文件，再发送更新日志。上传、通知和公告分别记录状态，避免重跑时重复发布。

用户数据与程序安装分离，覆盖升级不替换登录凭据。已有 WebView2 时直接复用，缺少时联网安装，减少安装包体积。

## 验证范围

验证覆盖单元测试、分发界面检查、冻结程序自检和隔离安装升级验收。自动化交易测试使用模拟响应，不代表对所有平台实时交易行为或长期可用性的保证。

当前展示不提供未经测量的并发量、速度提升比例、用户规模或收益指标。后续可持续积累可复现的性能基线、版本记录和问题修复案例。
